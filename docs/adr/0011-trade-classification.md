# 0011 — 买卖线索与客户采购询盘分开

## 问题

`summarize_inquiry@4` 把供应商供货目录当 promotion，而界面只认采购询价和 business。
CPU/SSD/HDD/GPU/Motherboard/RAM 报价、DRAM/eMMC 现货因此落入「其他邮件」。
工作台要突出所有具体买卖沟通；这不能靠产品关键词或发件人白名单实现。

## 决定

`summarize_inquiry@5` 要求模型明确输出 `is_trade` 和 `trade_role`：

| 含义 | mail_type | is_trade | trade_role |
| --- | --- | --- | --- |
| 客户新增采购、询价、修改需求重新报价 | inquiry | true | buyer |
| 供应商供货、现货目录、产品报价 | business | true | supplier |
| 既有买卖的确认、议价、执行、评测、丢单跟进 | business | true | transaction |
| 被动账单、AR aging、对账单 | billing | false | none |
| 新闻、系统通知、泛化营销 | 原有对应类型 | false | none |
| 内容不足，无法判断买卖意图 | other | false | uncertain |

分类依据本封新增内容；历史与附件仅作为原文上下文。正文内要求模型改变规则的
指令是邮件数据，不执行。银行安全提醒不因发件人是银行而变成账单；供应商的
账龄表不因同一客户存在产品订单而变成新买卖沟通。

`is_inquiry` 保留采购需求语义。供应商也显示 SALES LEAD，但不会被自动填入采购方
`lead_suggestion`，不修改人确认过的 `lead`、销售进度、文件夹或对外发送授权。
字段一致性是可穷举的合同约束：采购询盘必为 buyer 交易；none/uncertain 必为非交易。
代码校验这些枚举约束，不读取正文猜分类。

新成功读数必须有两个新字段。持久化的旧读数无需修改，API 对没有 `is_trade` 的旧
JSON 保留 inquiry/business 兼容。新读数显式 `is_trade=false` 时不再被 business
兼容逻辑覆盖。每封原文只取其最新读数，重新判定不会沿用该原文的旧错误结果；
同一话题中其它原文的有效交易证据和人确认的线索仍可保持话题的交易标记。

## 历史重分类

`python -m aimail.reclassify` 是独立维护入口，默认只读检查，不调用模型；须明确传
`--apply` 才执行，默认最多 20 个话题，硬上限 100。只处理精确指定邮箱内未删除
话题的最新来信；不读取另一个邮箱的原文片段，不处理历史旧信和我方发件。
当前任务版本已有读数即跳过，失败重试须明确 `--retry-failed`。批次用文件锁防止
维护命令互相重叠，不在模型等待时占用数据库事务。每个读数至多有一次结构修复，
检查输出另列最多任务尝试数；不能把 20 个话题说成精确只花 20 次模型调用。

重分类新增带来源、模型、任务版本、时间的派生读数，不更新或删除原文，也不重新
提采购线索建议。服务器正常启动不会自动执行历史批次；界面逐话题「重新分析」
仍可使用。部署新代码不表示旧邮件已经重新分类，须在生产主机明确执行并核验结果。
