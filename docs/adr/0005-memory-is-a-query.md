# 0005 记忆是一次查询,不是一张模型写的表

日期:2026-09-19 · 状态:已采纳 · 依据:CONSTITUTION.md 第一、三、四条;docs/adr/0003-sqlite-first.md

## 决定

- 「同一位客户」由代码裁决:同一个邮箱地址,或同一个公司域名;公共邮箱域(gmail、qq、163…)上只认整个地址。
  判据是 `store/history.py` 里一张可穷举的常量表,不是模型判断,不是相似度。
- 记忆没有自己的表。每次读信、起草时,从不可变的 `thread` / `message` / `lead` 现查这位客户在**同一邮箱**里的
  其他线程(最近五条),拼成一段带标题的文本放在模型输入末尾:主题、日期、我们记的状态(文件夹、线索结果)、
  最后一封来信的原文摘录。
- 历史段只含**原文摘录**和**我们自己记的状态**,不含任何模型输出(摘要、建议)。派生物不喂派生物;
  模型从历史里引用的数字仍然回得到原文,核对器照常工作(第四条)。
- 输入格式变了就是合同变了:`summarize_inquiry@1 → @2`、`draft_reply@1 → @2`,评测集各加一条「只有一句新内容」的样本。
- 界面上历史是线程详情的一部分(`GET /api/threads/{id}` 的 `history`),列表不带;第一次来信的客户在页头标出来。

## 为什么

- 客户的第二封信常常只有一句话(「同上次」「改成 32 台」),型号和数量都在上一条线程里。没有记忆,摘要只能写「未提及」。
- 现查比另存便宜且永远一致:原文不可变,查询结果就是确定的;没有第二份真相要同步,没有过期问题,零 schema 变更。
- 不喂模型输出是为了让「每个数字都能回到原文」这条保证在有记忆之后依然成立——否则一次幻觉会被下一次读数当作事实。
- 按邮箱隔离是 M9(第二个邮箱)的前提:两个邮箱互不可见,从第一天就是查询条件而不是事后加的过滤。

## 否决了什么

- 模型维护的「客户备忘」表(让模型每次更新一段客户画像):画像会漂移、会把幻觉固化,而且无法回到原文。
- 向量检索 / 嵌入相似度找「相关邮件」:多一套基础设施,而当前规模下按地址与域名精确匹配已经覆盖真实需要;
  相似度的语义规则也没法穷举。
- 把历史摘要(模型输出)放进上下文:违反「派生物不喂派生物」,见上。

## 推迟了什么

- 跨邮箱的客户视图(同一客户在 sales@ 与 support@ 的往来合看):等 M9 有第二个邮箱再定,届时也应是显式配置而不是默认。
- 以公司名(而非域名)归并客户、以及人工把两个域名标成同一家公司:等真实数据里出现再做,做也是人来标、代码来用。
- 五条以外的更长历史或按时间衰减:等评测集里出现需要它的样本。
